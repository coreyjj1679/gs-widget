# 2026-10-24 頁面載入效能量測

本次在 Apple M5、24 GiB 記憶體、macOS 上，使用 1.2.1 的 release／aarch64 建置，量測 20 個主要入口狀態。這些狀態的首次同步處理加軟體快照為 **3.3–41.9 ms**，五次重訪中位數為 **3.1–31.2 ms**；本次範圍內沒有重現超過 1,000 ms 的頁面停頓。這不是使用者 Ryzen 9 電腦上的結果，也沒有涵蓋所有詳細頁、分類、搜尋條件與滾動位置。

10 月 24 日原始資料：[頁面量測 pages.json](performance/2026-10-24/pages.json)、[資料與圖示量測 catalog.json](performance/2026-10-24/catalog.json)。10 月 25 日另補正常應用程式的原生操作驗證，見本文末段與 [native-summary.json](performance/2026-10-24/native-summary.json)。原始數值保留完整精度；本文頁面時間四捨五入至 0.1 ms。未將可能包含已儲存計算價格的畫面快照加入儲存庫。

**量測方法。** 視窗固定為 1280 × 800、縮放 1×、全模式、zh-en，使用 Slint `winit-software` renderer；怪物圖庫關閉。每個狀態量測第一次進入及五次重訪，重訪前先切到中立頁面並產生一次不計時快照，以卸載目標 UI。全部狀態共用同一程序、catalog 與快取；「首次」發生在計算器預先初始化之後，並非每頁獨立冷啟動，也沒有清除作業系統磁碟快取。實作見 [perf_pages.rs](../widget/src/perf_pages.rs#L136)。

`prep_ms` 是同步資料查詢、列資料與模型準備，包含同步圖示取得及非同步圖示工作的入隊；`render_ms` 是 Slint 版面配置與 CPU 快照光柵化；`total_ms` 包含兩者。各欄位的中位數分別計算，因此兩個中位數相加不一定等於總時間中位數。快照編碼和寫入磁碟不計時。

非同步圖示工作只計數後丟棄，沒有執行解碼、UI 回填或圖片上傳；本報告也不包含事件迴圈排程延遲、原生畫面呈現、網路及更新檢查。因此數值代表真實資料模型加第一張軟體快照的成本，不能當作原生視窗全部圖片載入完成的時間，也不能直接換算成 Windows GPU renderer 的體感延遲。

**較值得追蹤的部分。** 怪物全部有 844 筆，重訪資料準備中位數 25.5 ms、快照 5.7 ms；另排入 9,915 個未執行的圖示工作，工作數不是獨立圖片數。任務全部有 933 筆，資料準備 19.2 ms、快照 4.2 ms。NPC 有 1,133 筆，資料準備只有 1.5 ms，快照為 22.5 ms；商店入口預先顯示 996 筆，快照為 17.3 ms。這些結果可用來安排後續原生 UI 與圖示流程的量測。

計算三個狀態代表從首頁重新進入「計算」，並指定所見分頁；每次會執行共同的 `calculator_refresh`，同時更新道具及角色模型。原生 UI 在已開啟的計算器內切換分頁只變更可見狀態，不會再次 refresh，因此本文 22.0–25.3 ms 的重訪數值不能當作純分頁切換時間。紅利候選資料在啟動時已準備好。見 [計算器 refresh](../widget/src/calculator_ui.rs#L808) 與 [分頁點擊](../widget/ui/app.slint#L7770)。此次道具計算器有 40 個候選、4 個材料列；角色 209 個候選、紅利 186 個候選，後兩者沒有選中的材料／樹模型。

怪物全部使用 `publish` 重建目錄、地區與結果；實際從怪物目錄點選「全部」會走保留目錄及部分快取的 `reload_board`，故此項是完整狀態重建成本，可能高於那一次點擊。見 [測試狀態準備](../widget/src/perf_pages.rs#L64)、[原生 reload_board](../widget/src/main.rs#L79)。設定別名項包含選擇該分頁時的 refresh；若直接重新開啟已選中的別名頁，原生 UI 會保留模型。此處為 2 個別名、9 個浮動列項目，首頁收藏為 0 筆；不同使用資料可能改變成本。

**診斷初始化。** 第一次頁面快照前的診斷初始化共 **709.9 ms**。這只涵蓋此測試程式啟用的初始化子集，並非完整原生應用程式從啟動到可操作的時間：

- 使用資料初始化：0.049 ms。
- Catalog 開啟：305.8 ms。
- Backend 與 App 建立：214.5 ms。
- 道具與角色計算器初始化：163.6 ms。
- 紅利計算器初始化：18.1 ms。
- 導覽圖片、別名與版本歷史：6.4 ms。
- 顯示視窗與設定尺寸：1.5 ms。

紅利初始化雖然會重複列舉候選角色與建立樹，但實測僅 **18.1 ms**，不是本輪主要耗時來源。道具與角色計算器初始化為 163.6 ms，Catalog 開啟為 305.8 ms；仍需完整原生啟動 trace 才能判斷使用者等待時間落在哪個階段。

**獨立 Catalog 測試。** 另一個程序量測了 103 個資料／圖示情境，排除 GUI 配置、渲染、事件迴圈和圖片上傳。以下為中位數，單次情境則列該次時間：

- Catalog 開啟（單次）：291.391 ms。
- 1,000 個圖示首次解碼批次（單次，程序快取尚未有這批資料）：19.448 ms。
- 相同 1,000 個圖示的快取批次：0.349 ms。
- 844 筆怪物卡片資料：13.865 ms。
- 道具搜尋 a（7,951 筆）：5.397 ms。
- 道具模糊搜尋（1 筆）：3.330 ms。
- 更新資料搜尋龍（109 筆）：3.104 ms。
- 中國商店分區資料（4,347 筆）：1.384 ms。
- 材料分區資料（1,920 筆）：0.694 ms。
- 強化配方分區資料（1,526 筆）：0.359 ms。

圖示候選共 4,291 個，按固定排序取其中 1,000 個；全部樣本解碼失敗數為 0。首次解碼沒有清除 OS 磁碟快取，快取批次也不代表重新解碼。Catalog 的搜尋／分區查詢只量測取得資料，不包含對應頁面的完整列資料加工和畫面；尤其 `search.quest.root` 與全模式任務總覽不是相同 UI 路徑，不能互相替代。

**程式碼觀察與後續驗證。** 目錄導覽在 UI 回呼中同步呼叫 [list::publish](../widget/src/main.rs#L723)；[show_rows](../widget/src/list.rs#L960) 會加工整份結果並排入圖片工作。[cached_icon](../widget/src/icons.rs#L820) 在快取未命中時同步解碼，其他圖片則由 [背景工作程序](../widget/src/icons.rs#L36) 分批解碼後回填 UI。這些結構可能使多核心 CPU 的總運算能力無法直接消除單次 UI 等待，但程式碼結構與本次快照量測尚不能證明它們就是 Ryzen 9 卡頓的原因。

**2026-10-25 原生操作驗證。** 使用同一台 Apple M5、24 GiB、macOS、1.2.1 release／aarch64，啟動正常應用程式並實際點擊頁面。此輪沿用應用程式預設 renderer，未確定實際 GPU／renderer 名稱；視窗為 1414 × 907 邏輯像素、2× 縮放，語言為單語 zh。隔離設定中的 zh-en 未被 `parse_languages` 接受而回落至 zh，因此不能與前述 zh-en、1× 軟體快照當作同條件比較。量測期間沒有並行編譯工作。
